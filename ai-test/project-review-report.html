ZConect — глубокий анализ проекта (статическое ревью)

Проект: romantic-noyce
Дата отчёта: 2026-04-07
Состав: сервер Go (server/), клиент WPF .NET 8 (client/)

Короткое резюме

Есть 2 логических дефекта в управлении сессиями на сервере, которые могут ломать безопасность/ожидаемое поведение (закрытые сессии потенциально можно “поднять” через join; утечки индексов по machine_id).
В клиенте есть несколько источников “тихих” сбоев: async void обработчики и широкие catch { /* ignore */ }, а также принудительный Environment.Exit(0).
Примечание: запуск go test в текущей среде не выполнен — команда go не найдена (Go SDK не установлен/не в PATH). Это отражено ниже как ограничение проверки.

Результаты сборки/проверок

.NET (client)

  • Сборка успешна: dotnet build client/UiApp/UiApp.sln -c Release
  • Предупреждение: NETSDK1206 — обнаружены RID win10-x64, win10-x86 у зависимости Microsoft.MixedReality.WebRTC. Риск: в .NET 8+ ресурсы version-specific RID могут не резолвиться по умолчанию.

Go (server)

  • Ограничение окружения: go test ./... не выполнен, т.к. go не найден в системе.

Ошибки и риски (для исправления)

CRITICAL Закрытие сессии не разрывает привязку логина → session_id
Симптом: после POST /api/v1/session/close логин-код остаётся в sessionByLogin. Метод Join не проверяет StateClosed, поэтому закрытую, но ещё не истёкшую сессию можно снова “подключить”.
Где: server/internal/session/service.go — Close() и Join()
// Close(): не удаляет sessionByLogin[loginCode]
// Join(): не проверяет sess.State == StateClosed
Рекомендация: в Close() удалять индекс sessionByLogin (и, по желанию, sessionsByID), либо в Join() явно отвергать StateClosed (и/или переводить ExpiresAt в прошлое при close).
CRITICAL PruneExpired не чистит индекс machine_id → session_id
Симптом: PruneExpired() удаляет только sessionsByID и sessionByLogin, но не sessionByMachine. Это приводит к “висячим” ссылкам и потенциально неверному reuse сессий при CreateWithOpts(MachineID).
Где: server/internal/session/prune.go
Рекомендация: при удалении сессии также удалять sessionByMachine[sess.MachineID], если MachineID задан.
HIGH WS токен передаётся в query string
Риск: токены в URL часто попадают в логи прокси/балансировщиков, в историю, в телеметрию, могут утечь через реферер при редиректах (в браузерном мире) и т.п. Для desktop‑клиента риск ниже, но на бою лучше не закреплять паттерн.
Где: server/internal/signaling/handler.go (берёт ?token=)
Рекомендация: перенос токена в заголовок (например, Authorization: Bearer) или в Sec-WebSocket-Protocol, либо выдавать одноразовый WS-токен и логировать URL без query.
HIGH X-Forwarded-For используется без нормализации
Риск: rate limit можно обходить/ломать подставным X-Forwarded-For, если сервис доступен напрямую (не только за доверенным прокси) или если прокси не очищает заголовок.
Где: server/internal/ratelimit/ratelimit.go (extractIP)
Рекомендация: доверять X-Forwarded-For только если запрос пришёл от доверенного reverse-proxy (allowlist подсетей) и парсить первый IP через строгий парсер (net.ParseIP).
HIGH panic на старте сервера / генерации секретов
Риск: неуправляемое завершение процесса вместо корректного лога/выхода с кодом/метрики. На сервере лучше “проваливаться” с понятной причиной, но без паники (или хотя бы логировать через stderr и выходить).
Где: server/cmd/signaling/main.go (ошибка logger) и server/internal/auth/token.go (ошибка rand.Read).
Рекомендация: заменить panic на возврат ошибки/лог + os.Exit(1) (или поднять ошибку до main), чтобы поведение было предсказуемым.
MED Игнорирование ошибок в критических местах
Это усложняет диагностику и маскирует деградацию. Примеры: server.Shutdown, json.Encoder.Encode, Conn.Set*Deadline, file.Write, w.Write.
Где (примеры): server/cmd/signaling/main.go, server/internal/api/handler.go, server/internal/signaling/handler.go, server/internal/logging/logger.go, server/internal/ratelimit/ratelimit.go
Рекомендация: не обязательно “везде возвращать ошибку наверх”, но логировать (с rate-limit на логи) там, где ошибка может менять поведение.
MED Client: async void (кроме UI event handlers) + риск неотловленных исключений
В WPF async void допустим для событий, но в инфраструктуре/координаторах это делает ошибки “тихими” и плохо тестируемыми. В частности, в WebRtcTransport/SignalingCoordinator.cs обработчики и flush — async void и ловят исключения, но продолжают выполнение без сигнализации наверх.
Где: client/WebRtcTransport/SignalingCoordinator.cs (FlushEarlyCandidates, OnMessageReceived, OnLocalIceGenerated), client/UiApp/Commands/RelayCommand.cs (AsyncRelayCommand.Execute)
Рекомендация: перевести на Task-цепочки (или очередь/канал обработки сообщений), а в ICommand — централизованно логировать исключения и показывать UI-ошибку.
MED Client: принудительный Environment.Exit(0) при закрытии окна
Риск: обрываются фоновые операции (файлы/лог/WS), могут не успеть отработать Dispose, возможна потеря данных/неконсистентное состояние. Также “глушит” проблему, если приложение зависает при корректном shutdown.
Где: client/UiApp/MainWindow.xaml.cs (OnClosingAsync)
Рекомендация: фиксировать первопричину зависаний (если они были) и уходить на штатный Application.Current.Shutdown() без Environment.Exit. Если нужен “hard-exit”, оставить как fallback по таймауту, но с логом причины.
CRITICAL File Transfer: потенциальная запись файла в произвольное место (path traversal / arbitrary write)
На приёме файла путь назначения строится из TargetDirectory и/или RelativePath, пришедших с удалённой стороны. Сейчас нет нормализации/ограничения корня: можно подсунуть .., абсолютный путь, UNC-путь и т.п., и записать файл вне “папки полученных”. Это особенно критично, т.к. приложение часто запускается с админ‑правами.
Где: client/FileTransfer/FileTransferService.cs — OnFileEndReceived (формирование saveDir/finalPath)
// saveDir берётся из payload.TargetDirectory (удалённая сторона управляет!)
// finalPath = Path.Combine(saveDir, state.RelativePath ...)
Рекомендация: принимать только “безопасный относительный путь” (без .., без двоеточий/UNC, без ведущих слешей), а итоговый путь валидировать через Path.GetFullPath и проверку, что он лежит внутри разрешённого корня (например, папки приёма).
CRITICAL Remote File Panel (host): удалённая сторона может читать/удалять файлы и создавать папки по произвольным путям
Обработчики запросов через data channel (dir_list_request, file_request, delete_request, create_folder_request) принимают “путь как есть” и выполняют операции ФС. Сейчас нет аутентификации на уровне команд, нет ограничений по разрешённым директориям, нет подтверждения со стороны пользователя host. В итоге viewer (или злоумышленник, получивший доступ к каналу) потенциально может: 1) запросить отправку любого файла (file_request), 2) удалить любой файл/папку (delete_request), 3) создавать каталоги в произвольных местах.
Где: client/UiApp/ViewModels/MainViewModel.FileTransfer.cs — OnDirListRequestReceived, OnFileRequestReceived, OnDeleteRequestReceived, OnCreateFolderRequestReceived
Рекомендация: ввести “sandbox” (разрешённые корни, например только выбранная папка/Downloads), обязательное подтверждение для опасных операций (delete / отправка файла), и строгую нормализацию пути (reject абсолютных/UNC/с ..).
HIGH FileTransferService: fire-and-forget вызов ProcessQueueAsync сделан некорректно
В EnqueueSend и EnqueueSendFolder используется ProcessQueueAsync().ConfigureAwait(false); без await и без присваивания в _ =. Это выглядит как попытка “запустить фоном”, но в текущем виде легко потерять исключения и сделать поведение зависимым от деталей планировщика.
Где: client/FileTransfer/FileTransferService.cs — EnqueueSend, EnqueueSendFolder
Рекомендация: заменить на _ = ProcessQueueAsync(); (и логировать исключения внутри), либо явно возвращать Task наружу и await’ить из UI/VM слоя.
MED Remote dir list: расчёт размера папки может “убить” поток обработки сообщений
GetDirectorySizeSafe делает EnumerateFiles(..., AllDirectories).Sum(...), что на больших/сетевых каталогах может занять секунды/минуты. Это выполняется прямо в обработчике входящего сообщения и может приводить к лагам/таймаутам/потере responsiveness.
Где: client/UiApp/ViewModels/MainViewModel.FileTransfer.cs — GetDirectorySizeSafe и вызов при листинге директорий
Рекомендация: убрать размер папки из ответа (или сделать опциональным), либо считать его асинхронно/постепенно с лимитами и кешем.
HIGH Захват/передача видео: блокировка потока захвата из‑за Sleep внутри lock
В цикле захвата кадра есть участок, который берёт lock (_captureSync) и при отсутствии настроек/буферов делает Thread.Sleep(10), не отпуская lock. Это может блокировать конкурентные операции, которым тоже нужен этот lock (например, коллбек выдачи кадра в WebRTC), что проявляется как “дёрганье”, периодические паузы или зависание кадра при реконфиге.
Где: client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs — CaptureLoopThread()
Рекомендация: не спать под lock: вынести проверку/ожидание за пределы lock, либо использовать Monitor.Wait/Pulse или ManualResetEventSlim для сигнализации “ресурсы готовы”.
HIGH Захват/передача видео: тяжёлый путь масштабирования через GDI Bitmap на каждый кадр
При масштабировании (DXGI single/multi) создаётся Bitmap на основе сырого буфера (using var srcBmp = new Bitmap(...)) и затем выполняется DrawImage + LockBits + Marshal.Copy в буфер кадра. Это даёт существенную нагрузку на CPU/GDI, большое количество unmanaged объектов и может стать узким местом при 30fps+ или высоких разрешениях.
Где: client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs — CaptureDxgi()/CaptureDxgiMulti() (ветки scaling)
Рекомендация: перейти на GPU scaling (D3D11 shader/CopySubresourceRegion), либо на более лёгкий CPU scaler без GDI, либо хотя бы реюзать объекты и минимизировать Bitmap/Graphics churn.
MED Viewer: двойное копирование кадров (unmanaged → managed → WriteableBitmap)
На viewer стороне кадр копируется из unmanaged указателя в managed byte[] (Marshal.Copy), затем ещё раз копируется в backbuffer WriteableBitmap на UI потоке. Это увеличивает задержку, загрузку CPU и давление на GC при высоких FPS/разрешениях (даже с маленьким пулом).
Где: client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs — OnArgb32RemoteVideoFrameReady, и client/UiApp/ViewModels/MainViewModel.Video.cs — OnRemoteVideoFrameReceived
Рекомендация: рассмотреть прямую отрисовку через D3D shared texture / D3DImage (минимум копий), либо “последний кадр” с дропом промежуточных (backpressure), чтобы UI не захлёбывался.
MED Viewer: риск накапливания UI-постов при перегрузке (нет backpressure)
Для каждого принятого кадра делается _uiContext.Post(...). Если UI поток не успевает (ресайз окна, GC, нагрузка), очередь сообщений растёт — увеличивается latency, появляются “рывки” (старые кадры рисуются позже). Пул буферов ограничен (Count < 4), поэтому при накоплении постов начнутся новые аллокации.
Где: client/UiApp/ViewModels/MainViewModel.Video.cs — OnRemoteVideoFrameReceived, client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs — пул _viewerBufferPool
Рекомендация: сделать стратегию “рисовать только последний кадр”: хранить latestFrame, ставить флаг renderScheduled и планировать максимум один UI update за тик/кадр.
CRITICAL Host: удалённая сторона может инициировать опасные действия (SAS Ctrl+Alt+Del) без подтверждения
При получении сообщения ctrl_alt_del host вызывает WindowsInputInjectionService.SendCtrlAltDel(). Внутри сервис также пытается выставить системную политику реестра SoftwareSASGeneration, чтобы разрешить генерацию SAS. Это действие повышает привилегии удалённого управления на хосте и должно быть под явным контролем пользователя.
Где: client/UiApp/ViewModels/MainViewModel.Input.cs — OnCtrlAltDelReceived, client/UiApp/Services/WindowsInputInjectionService.cs — SendCtrlAltDel/EnsureSoftwareSasPolicy
Рекомендация: добавить подтверждение на host (и/или флажок “разрешить Ctrl+Alt+Del” по умолчанию выключен), логировать попытки, а изменение политики реестра делать только по явной команде пользователя (не “молчаливо” из сетевого события).
HIGH Host: удалённая сторона может инициировать удалённое управление вводом без явной “сессии доверия”
При режиме host обработчики MouseReceived/KeyboardReceived сразу инжектят ввод через WinAPI. В текущем протоколе (data channel) нет отдельной авторизации/капабилити‑флага на “управление вводом” (всё держится на факте установления WebRTC). При расширении функциональности (адресная книга/персистентные host‑сессии) это важно явно моделировать.
Где: client/UiApp/ViewModels/MainViewModel.Connection.cs — WireUpDataChannelCoordinator(role==Host), client/UiApp/ViewModels/MainViewModel.Input.cs — OnMouseInputReceived/OnKeyboardInputReceived
Рекомендация: ввести явный “grant control” на host (подтверждение/таймаут/ревокация), и возможность “только просмотр/только файлы” на уровне разрешений команд data channel.
HIGH Host: чувствительные данные (коды/последняя сессия) сохраняются в AppData в открытом виде
В ClientSettings сохраняются LastSessionId, LastLoginCode, LastPassCode, а также MachineId. Это упрощает UX, но увеличивает риск при компрометации профиля пользователя/малвари: можно восстановить коды, понять наличие активной “unattended” конфигурации и т.п.
Где: client/UiApp/Services/SettingsService.cs, client/UiApp/Models/ClientSettings.cs, запись выполняется из client/UiApp/ViewModels/MainViewModel.Connection.cs
Рекомендация: хранить минимум необходимого; для секретов использовать DPAPI (ProtectedData) или шифрование, либо не сохранять LastPassCode вообще (только session_id + machine_id, если сервер поддерживает переиспользование).
MED Host: WS-reconnect вызывает RefreshSession (может неожиданно ротировать пароль/TTL)
В WsReconnectLoopAsync перед переподключением WS вызывается RefreshSessionAsync для получения нового ws_token. На сервере refresh также меняет pass_code и продлевает TTL. Это может быть неожиданным побочным эффектом “просто переподключить WS”.
Где: client/UiApp/ViewModels/MainViewModel.Connection.cs — WsReconnectLoopAsync, client/SessionClient/SessionApiClient.cs
Рекомендация: выделить отдельный endpoint “refresh ws_token” без ротации пароля (или добавить флаг), либо на клиенте явно учитывать, что refresh меняет пароль (обновлять UI/копирование/историю и т.п.).
HIGH ICE upgrade: монитор заявлен “для обоих ролей”, но запускается только у viewer
StartIceUpgradeMonitor() содержит явную проверку if (_role != Viewer) return;, однако комментарии у IceUpgradeMonitorLoopAsync говорят “Works for both Viewer and Host roles” и внутри цикла есть проверки допускающие Host. Это рассинхрон документации/логики и часто признак недоделанного поведения: host никогда не будет инициировать улучшение маршрута (что ок), но код “как будто” это поддерживает.
Где: client/UiApp/ViewModels/MainViewModel.Connection.cs — StartIceUpgradeMonitor, IceUpgradeMonitorLoopAsync
Рекомендация: либо чётко задокументировать “только viewer инициирует ICE restart”, либо расширить дизайн, если планировалось иначе (например, host может инициировать restart при деградации).
HIGH ICE upgrade: GetAdaptiveInterval принимает RTT, но не использует его
Метод GetAdaptiveInterval(route, consecutiveRelayCount, rttMs) игнорирует rttMs. В результате логика “RTT drops/degrades” фактически не влияет на частоту проверок, и модель “адаптивности” работает только по счётчику relay.
Где: client/UiApp/ViewModels/MainViewModel.Connection.cs — GetAdaptiveInterval
Рекомендация: либо убрать параметр (чтобы не вводить в заблуждение), либо реально использовать RTT (например, чаще проверять при высоком RTT/джиттере даже на srflx, или при деградации на “оптимальном” маршруте).
MED ICE upgrade: возможна гонка по sessionId при переподключении/новой сессии
В монитор передаётся строковый sessionId параметром и он используется в цикле/ICE restart. При реконнекте/смене сессии _currentSessionId меняется, но монитор может продолжить работать со старым sessionId, если его не отменили вовремя. Частично это нивелируется отменой через _lifetimeCts, но это всё равно хрупко при сложных сценариях (быстрый reconnect + новый join/create).
Где: client/UiApp/ViewModels/MainViewModel.Connection.cs — StartIceUpgradeMonitor(sessionId, ct), IceUpgradeMonitorLoopAsync(sessionId,...), PerformIceRestartAsync(sessionId,...)
Рекомендация: внутри цикла сверять sessionId с _currentSessionId и выходить, если они разошлись; аналогично перед каждым restart.
MED ICE route detection основан на “наблюдаемых” типах кандидатов, а не на реально выбранной паре
_localIceCandidateType/_remoteIceCandidateType обновляются из IceCandidateObserved и по сути являются эвристикой (“лучший увиденный тип”). Затем InferRouteType принимает решение по этим двум строкам. Это может ошибаться относительно фактического маршрута (selected candidate pair), а значит может ошибочно: - не запускать upgrade, когда реально сидим на TURN, - либо запускать restart, когда маршрут уже хороший, - либо показывать неверный статус в UI.
Где: client/UiApp/ViewModels/MainViewModel.Ice.cs — OnIceCandidateObserved/InferRouteType, client/UiApp/ViewModels/MainViewModel.Connection.cs — использование InferRouteType в Auto ICE и upgrade monitor
Рекомендация: определять маршрут по stats/selected candidate pair (например, через WebRTC stats / selectedCandidatePairId), а “observed candidates” оставить только как debug‑подсказку.
MED ICE upgrade: обновление типа кандидатов происходит через UI-post → задержка/рассинхрон с монитором
OnIceCandidateObserved делает _uiContext.Post(...), и уже внутри поста обновляет поля маршрута. Монитор IceUpgradeMonitorLoopAsync читает эти поля в фоновом потоке. Если UI поток загружен, обновления кандидатов будут приходить с задержкой, а monitor будет опираться на устаревшие значения, что повышает вероятность ложных “unknown” и неверных решений.
Где: client/UiApp/ViewModels/MainViewModel.Ice.cs, client/UiApp/ViewModels/MainViewModel.Connection.cs
Рекомендация: отделить “логирование/обновление UI” от “обновления состояния маршрута”: состояние обновлять в вызывающем потоке (thread-safe), а UI текст — отдельно постить.
HIGH Viewer: отправка ввода запускается через Task.Run на каждое событие (риск перегруза/очередей)
HandleRemoteSurfaceMouseMove/Down/Up/Wheel и клавиатура вызывают SafeSendMouseAsync/SafeSendKeyboardAsync, которые внутри делают Task.Run(async () => ...) на каждое событие. При высокой частоте (move, wheel, key repeat) это может создавать лавину задач, повышать latency и ухудшать стабильность канала (особенно на слабых CPU).
Где: client/UiApp/ViewModels/MainViewModel.Input.cs — SafeSendMouseAsync, SafeSendKeyboardAsync
Рекомендация: заменить на один сериализованный sender-loop (Channel/BlockingCollection) или хотя бы не использовать Task.Run для уже async методов (вызывать dc.Send* напрямую с throttling/coalescing).
HIGH Viewer: отсутствует backpressure/coalescing для мыши (кроме 16мс throttle)
Есть только ограничение по времени (16мс) и фильтр “те же координаты”, но при перегрузке/плохой сети задачи на отправку всё равно накапливаются. В итоге host может получать “устаревшие” движения, а управление станет дерганым.
Где: client/UiApp/ViewModels/MainViewModel.Input.cs — HandleRemoteSurfaceMouseMove
Рекомендация: хранить только “последнюю позицию” и отправлять её с фиксированным тикером (например 60Гц) или по готовности канала; при перегрузе — дропать промежуточные.
MED Viewer: возможны “залипшие клавиши” при сетевых сбоях/потере фокуса
Viewer ведёт локальный набор нажатых VK и при потере фокуса пытается отправить “key up” для всех. Но отправка — fire-and-forget и может не дойти (канал закрывается/lag), а host продолжит считать клавишу зажатой.
Где: client/UiApp/ViewModels/MainViewModel.Input.cs — ReleaseAllPressedKeys, HandleRemoteSurfaceLostFocus
Рекомендация: добавить протокол “reset input state” (на host стороне очистить/отпустить модификаторы по спец-команде), либо периодический watchdog на host (если нет input N секунд — отпустить).
MED Viewer: подключение не учитывает require_confirm от сервера/хоста
API join возвращает require_confirm, но viewer-ветка не делает отдельного flow ожидания подтверждения/отказа. Сейчас сразу строится WS/WebRTC. Если на сервере/host предполагается подтверждение, нужен явный протокол состояния (pending/approved/denied) и UX ожидания.
Где: client/SessionClient/Models.cs (поле RequireConfirm), client/UiApp/ViewModels/MainViewModel.Connection.cs — ConnectAsViewerAsync
Рекомендация: реализовать подтверждение на уровне протокола (например, host отправляет approve по dc-control/WS), а viewer показывает “Ожидание подтверждения…” и не включает инжект ввода до approve.
MED Viewer: Ctrl+Alt+Del доступен всегда (нет явного согласия/политики)
В окне viewer есть кнопка Ctrl+Alt+Del, которая отправляет команду на host. С учётом того, что host выполняет её без подтверждения (см. отдельный CRITICAL пункт), это усиливает риск “опасных действий одним кликом”.
Где: client/UiApp/RemoteScreenWindow.xaml — кнопка Ctrl+Alt+Del, client/UiApp/ViewModels/MainViewModel.Input.cs — SendCtrlAltDelAsync
Рекомендация: показывать кнопку только если host явно разрешил capability (и/или после approve), либо добавлять локальное подтверждение и аудит-лог.
HIGH Signaling WS client: нет ограничения размера входящих сообщений → риск OOM/DoS
WebSocketSignalingClient.ReceiveLoopAsync копит фреймы в MemoryStream до EndOfMessage, затем делает ms.ToArray(). При отсутствии лимита на длину сообщения злоумышленник/ошибка на сервере может прислать очень большой JSON и вызвать резкий рост памяти/краш клиента. На сервере сейчас есть лимит 64KB, но клиент не должен на это полагаться.
Где: client/WebRtcTransport/WebSocketSignalingClient.cs — ReceiveLoopAsync
Рекомендация: добавить max message size (например 256KB) и прерывать соединение/дропать сообщение при превышении, без аллокации полного буфера.
HIGH DataChannel protocol: отсутствуют лимиты/валидация размеров payload (dir_list, clipboard, file meta) → риск DoS
Для text сообщений data channel нет проверки длины raw до JsonSerializer.Deserialize. Для некоторых payload (например, DirListResponsePayload.Items) теоретически можно прислать огромный список и уронить UI/память. Для clipboard лимит реализован, но на обработке входящего всё равно используется fire-and-forget.
Где: client/WebRtcTransport/DataChannelCoordinator.cs — OnMessageReceived, client/WebRtcTransport/MixedRealityDataChannelAgent.cs — получение bytes→string
Рекомендация: ввести лимиты: max длина текста per kind/type (например control 64KB, input 4KB, clipboard 300KB, dir_list items limit), и отбрасывать превышающие сообщения.
MED Clipboard receive: fire-and-forget Task.Run + возможная очередь задач
При получении clipboard создаётся Task.Run, который постит Clipboard.SetText на UI поток. При флуде сообщений можно получить очередь задач/постов и ухудшение отзывчивости.
Где: client/UiApp/ViewModels/MainViewModel.Clipboard.cs — OnClipboardReceived
Рекомендация: коалесить “последний текст” и применять не чаще N раз/сек; отбрасывать повтор/старые; не использовать Task.Run для простого async flow.
MED Require-confirm: поле API есть, но протокола подтверждения нет
JoinSessionResponse.RequireConfirm парсится, но нигде не используется для построения состояния “ожидание подтверждения/отказ”. Это создаёт разрыв между UX настройкой “RequireConfirmation” и реальным поведением viewer/host.
Где: client/SessionClient/Models.cs, client/SessionClient/SessionApiClient.cs, client/UiApp/ViewModels/MainViewModel.Connection.cs — ConnectAsViewerAsync
Рекомендация: добавить явный approve/deny протокол (WS или dc-control) и блокировать управление до approve.
LOW Семантика WSURL в API ответе относительная
Сейчас сервер возвращает WSURL: "/ws". Это удобно для локального dev, но клиенту нужен корректный абсолютный URL (wss/ws) с хостом/портом, особенно если API сидит за прокси.
Где: server/internal/api/handler.go
Рекомендация: либо возвращать абсолютный URL (с учётом X-Forwarded-Proto/Host при доверенном прокси), либо явно документировать, что клиент строит WSURL сам из ServerBaseUrl.

Предложения по оптимизации (качество / надёжность / производительность)

Сервер (Go)

  • Согласованность индексов сессий: выделить единый приватный метод удаления сессии, который чистит sessionsByID, sessionByLogin, sessionByMachine (и вызывать его из Close и PruneExpired).
  • Rate limiting: отделить лимиты для /ws от API (handshake и долгие коннекты); плюс нормализация IP/заголовков за прокси.
  • WebSocket: добавить контекст отмены на чтение/пинг, обработку CloseMessage, метрики по причинам дисконнекта; логировать ошибки WriteMessage (хотя бы на debug).
  • Токены: если планируется горизонтальное масштабирование/рестарты — хранить секрет HMAC стабильно (env/secret manager), иначе токены отвалятся при рестарте; либо явно задокументировать, что токены короткоживущие и рестарт сбрасывает их (это нормально для MVP).

Клиент (WPF)

  • HttpClient: избегать частого new HttpClient() в тестах соединения (можно держать один экземпляр на всё приложение или использовать IHttpClientFactory если появится DI). Сейчас это не критично, но лучше закрепить практику.
  • async void: по возможности заменить на Task, где это не UI-событие, чтобы исключения не терялись и были тестируемыми.
  • Логи: сократить catch { /* ignore */ } в “важных” местах и хотя бы писать в debug-log причину (особенно для shutdown и file transfer).
  • RID warning (NETSDK1206): проверить рекомендации по RID usage (особенно для self-contained/publish), чтобы не словить “нет native dll” на другой версии Windows/в будущем SDK.

Что не хватает, чтобы конкурировать с AnyDesk (продуктовый разрыв)

Безопасность уровня продукта

  • Модель доверия/разрешений: отдельные права на просмотр/управление/файлы/буфер/Ctrl+Alt+Del/UAC, выдача/отзыв, видимый индикатор “кто управляет”.
  • Approve/deny flow: режим “с подтверждением” как явный протокол (pending→approved/denied) и блокировка опасных действий до approve.
  • Unattended в безопасном виде: allowlist устройств/контактов, политика паролей/TTL, ограничение команд, аудит.
  • Секреты и ключи: хранение чувствительных данных через DPAPI, ротация токенов, минимизация сохранения кодов/паролей.
  • Файлы: sandbox путей, защита от path traversal/arbitrary write, подтверждения для delete/выдачи файлов.

Надёжность соединения и сеть

  • TURN/STUN промышленного уровня: стабильный fallback, близкие регионы, корректные сценарии при VPN/sleep/switch networks.
  • Сервер сессий для продакшена: Redis/БД, горизонтальное масштабирование, HA, anti-abuse, токены без утечек в URL.
  • Reconnection без деградации: отсутствие накопления задач/подписок, предсказуемые таймауты и восстановление state.

Качество картинки и производительность

  • Аппаратное кодирование: H.264/H.265/AV1 (по возможностям), адаптивный bitrate по stats (loss/jitter/rtt).
  • Эффективный video pipeline: GPU scaling, минимум копий, backpressure “только последний кадр”.
  • Режимы: seamless multi-monitor, выбор окна/процесса, высокая DPI-качество, управление FPS/CPU.

Удалённое управление

  • Надёжный ввод: reset input state, предотвращение “залипания”, раскладки/IME, хоткеи, блокировка локального ввода, “privacy screen”.
  • UAC/secure desktop: корректный архитектурный подход (часто service-mode), а не изменение политик реестра из сетевых событий.

Продуктовые вещи (чтобы покупали)

  • Диагностика/телеметрия: connection report, экспорт логов, метрики ICE/WS/WebRTC, понятные коды ошибок.
  • Обновления и подпись: авто-апдейтер, подпись, каналы релизов.
  • Enterprise: роли/ACL, аудит, централизованная адресная книга, MSI/GPO/MDM деплой, режим сервиса.
  • Тестирование/CI: долгие прогоны, нагрузка, фуззинг протокола, статанализ и security review.

Быстрый план исправлений (по приоритету)

  1. Клиент (безопасность FT): закрыть path traversal/arbitrary write при приёме файла (валидировать TargetDirectory/RelativePath, ограничить корень сохранения).
  2. Клиент (безопасность remote FS): ограничить/подтверждать операции dir_list/file_request/delete/create_folder (sandbox + нормализация пути + UX подтверждения).
  3. Клиент (host безопасность): добавить явное разрешение/подтверждение на опасные команды (ввод, Ctrl+Alt+Del/SAS), и не менять политики реестра из сетевых событий.
  4. Клиент (секреты): не хранить коды/пароли в открытом виде в %AppData% (DPAPI/минимизация данных).
  5. Клиент (ICE): поправить/прояснить логику upgrade monitor (роль, sessionId), и определять текущий маршрут по реально выбранной candidate pair (stats), а не по эвристике “observed candidates”.
  6. Клиент (viewer ввод): убрать Task.Run на каждое событие ввода, добавить backpressure/coalescing для мыши и “reset input state” протокол от залипших клавиш.
  7. Клиент (confirm): реализовать require-confirm/approve flow, чтобы viewer не мог инжектить ввод/опасные команды до подтверждения хостом.
  8. Клиент (видео): убрать Sleep под lock в capture loop и добавить backpressure на viewer‑рендер (“только последний кадр”).
  9. Клиент (видео/CPU): оптимизировать scaling путь (уйти от GDI Bitmap на каждый кадр) и снизить число копирований кадров.
  10. Сервер: исправить Close()/Join() для закрытых сессий и синхронизировать очистку индексов (включая PruneExpired() + machine_id).
  11. Сервер: нормализовать IP для rate limit и доверие к X-Forwarded-For.
  12. Сервер: отказаться от токена в query (или минимизировать утечки/логирование), продумать стабильный secret для HMAC.
  13. Клиент: минимизировать async void и “тихие” catch там, где это влияет на UX/надёжность (signaling/file transfer/shutdown).
  14. Инфра: поставить Go SDK (если планируются server tests в CI) и добавить минимальный CI шаг: go test, go vet, dotnet test.
Этот отчёт сформирован по состоянию файлов в рабочем дереве. Если нужно — могу сразу внести правки в код и/или добавить CI-пайплайн.
