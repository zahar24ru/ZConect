File Transfer Review — romantic-noyce / ZConect

Отдельный технический отчёт по модулю передачи файлов: протокол, runtime-логика, баги, риски и улучшения.

Короткий вывод

Модуль передачи файлов уже сделан лучше среднего для MVP. Тут есть правильные инженерные решения: binary chunks вместо Base64, hash-проверка, temp-файл перед финальным перемещением, очередь отправки, поддержка передачи папок через relative path.

Но есть несколько важных мест, где логика пока не до конца корректна или недостаточно защищена.

Что анализировалось

  • client/FileTransfer/FileTransferService.cs
  • client/FileTransfer/DataChannelFileTransferChannel.cs
  • client/UiApp/ViewModels/MainViewModel.FileTransfer.cs
  • client/UiApp/FileTransferWindow.xaml.cs
  • client/WebRtcTransport/DataChannelCoordinator.cs
  • client/ZConect.Tests/FileTransferDiagnosticsTests.cs

Что уже хорошо

  • Binary chunk protocol — хороший выбор. Убран Base64-overhead на основном пути.
  • Есть hash verification на принимающей стороне.
  • Есть temp-file стратегия: сначала запись в .part, потом move в final path.
  • Есть очередь отправки, что упрощает lifecycle.
  • Есть передача папок через RelativePath.
  • Есть ACK/Error сообщения — это хорошая база для надёжного протокола.

1. Самая важная логическая ошибка: transfer считается успешным слишком рано

Файл: FileTransferService.cs

После отправки file_end sender сразу делает:

  • RaiseProgress(... Completed)
  • RaiseCompleted(...)

Но приёмник в этот момент ещё только:

  • закрывает stream,
  • считает hash,
  • перемещает файл в final destination,
  • и только потом шлёт ACK.

Проблема: UI отправителя может показать «файл успешно отправлен», а потом реально прийдёт отрицательный ACK или ошибка приёма.

Как должно быть:

  • после file_end outgoing transfer должен переходить в состояние Finishing / AwaitingAck;
  • в Completed он должен попадать только после ACK success=true.

2. Нет жёсткого лимита на размер входящего binary chunk

Файлы: DataChannelCoordinator.cs, FileTransferService.cs

На принимающей стороне пакет принимается целиком, chunk вырезается в новый массив, а затем может ещё и полностью распаковываться через GZip.

Риск:

  • memory pressure;
  • CPU spike на распаковке;
  • OOM / фризы при oversized payload.

Что улучшить: ввести явный лимит, например:

  • максимальный размер raw binary packet;
  • максимальный размер распакованного chunk;
  • abort transfer при нарушении лимитов.

3. GZip по каждому chunk отдельно — рабочий, но не самый удачный компромисс

Файл: FileTransferService.cs

Сейчас chunk либо отправляется как есть, либо отдельно gzip-сжимается, а на приёмнике отдельно распаковывается.

Минусы:

  • CPU overhead на каждый chunk;
  • слабая эффективность по сравнению с потоковым сжатием;
  • на части форматов выигрыш почти нулевой.

Это не критический баг, но место для оптимизации есть.

4. Подсчёт размера папок в dir list может тяжело тормозить

Файл: MainViewModel.FileTransfer.cs

Для каждой директории вызывается:

EnumerateFiles("*", SearchOption.AllDirectories).Sum(fi => fi.Length)

Почему это плохо:

  • очень дорого на больших каталогах;
  • может подвешивать interactive listing;
  • не очень подходит для control-channel запроса.

Лучше:

  • в обычном listing не считать recursive folder size вообще;
  • или считать только по отдельному «Properties» запросу;
  • или делать ленивую подгрузку.

5. Remote delete / create / file request слишком широкие по доверию

Файл: MainViewModel.FileTransfer.cs

Сейчас удалённая сторона может запрашивать операции над произвольными путями файловой системы host'а.

Для доверенной техподдержки это может быть ок, но с точки зрения безопасности это очень мощный канал управления.

Что бы я улучшил:

  • ограничить операции рабочим root/path scope;
  • ввести режим подтверждения опасных операций;
  • логировать такие действия отдельно и явно.

6. Queue есть, но semantically transfer state machine пока неполная

Сейчас у outgoing transfer есть состояния вроде:

  • InProgress
  • Paused
  • Completed
  • Failed

Но для корректного протокола не хватает хотя бы ещё одного явного состояния:

  • AwaitingAck

Именно оно позволит корректно отделить:

  • «байты уже отправлены»
  • от «получатель подтвердил успешный приём».

7. Использование relative path для папок — хорошее решение, но требует аккуратной валидации

Сейчас relative path передаётся и используется для построения final destination. Это удобно, но важно следить, чтобы не было path traversal-подобных сюрпризов, если когда-нибудь источник relative path станет менее доверенным.

Сейчас у тебя путь выглядит контролируемым, но это место лучше заранее держать под контролем.

8. Тесты по file transfer пока больше диагностические, чем поведенческие

Файл: ZConect.Tests/FileTransferDiagnosticsTests.cs

Текущие тесты полезны, но в основном проверяют сериализацию payload и RequestId matching.

Чего не хватает:

  • теста на ACK lifecycle;
  • теста на sequence mismatch;
  • теста на hash mismatch;
  • теста на cancel/pause/resume;
  • теста на relative-path folder receive.

Итог

Модуль передачи файлов у тебя уже реально хороший для стадии MVP. Его не надо переписывать. Его надо докрутить по корректности состояния, лимитам безопасности и поведению файловой панели. Если поправить это, он станет заметно взрослее и надёжнее.
