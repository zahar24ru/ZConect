Input & Clipboard Review — romantic-noyce / ZConect

Отдельный отчёт по передаче мыши, клавиатуры, курсора и буфера обмена.

Короткий вывод

Подсистема input/clipboard уже построена на хорошей базе: есть отдельные payload'ы, viewer-side coordinate mapping, host-side injection service, cursor sync, pressed-key tracking, clipboard echo suppression и release-all-keys on disconnect.

Но есть несколько важных логических и UX-рискованных мест: особенно вокруг клавиатурных модификаторов, fire-and-forget отправки input, и polling-based clipboard sync.

Что анализировалось

  • client/UiApp/ViewModels/MainViewModel.Input.cs
  • client/UiApp/ViewModels/MainViewModel.Clipboard.cs
  • client/UiApp/Services/WindowsInputInjectionService.cs
  • client/WebRtcTransport/DataChannelModels.cs
  • client/WebRtcTransport/DataChannelCoordinator.cs

Что уже хорошо

  • Coordinate mapping у viewer'а сделан аккуратно. Учтены масштаб, letterbox, capture rect.
  • Есть pressed key tracking и release-all при потере фокуса/cleanup.
  • Cursor shape sync отделён от основного mouse input потока.
  • Clipboard echo suppression уже есть — это хороший знак, потому что loopback здесь частая проблема.
  • Host-side injection вынесен в отдельный service, а не размазан по UI-коду.

1. Главный риск по клавиатуре: модификаторы передаются дважды в некоторых сценариях

Файл: WindowsInputInjectionService.cs

Сейчас логика такая:

  • для немодификаторных клавиш host перед нажатием/отпусканием основной клавиши сам нажимает/отпускает модификаторы из payload;
  • но сами модификаторы viewer также может отдельно слать как обычные key down/up события.

Риск: возможны дубли/несогласованность состояний Ctrl/Shift/Alt/Win, особенно при быстрых комбинациях или если сеть теряет часть input-событий.

Что лучше: выбрать одну модель:

  • либо modifiers живут как отдельные события и host не «оборачивает» ими обычные клавиши;
  • либо payload описывает chord, и viewer не шлёт modifier down/up отдельно.

2. Fire-and-forget отправка input скрывает ошибки и упорядочивание

Файл: MainViewModel.Input.cs

SafeSendMouseAsync() и SafeSendKeyboardAsync() запускают отдельные Task.Run и в случае проблем только quietly log'ируют debug.

Риски:

  • сложно понимать, что input path реально уже развалился;
  • сложно поддерживать строгий ordering для keyboard events;
  • часть ошибок может быть почти невидима пользователю.

Для responsiveness это ок, но transport-гарантии тут довольно слабые.

3. Mouse move throttling есть, но не привязано к реальной пропускной способности канала

Файл: MainViewModel.Input.cs

Сейчас движение мыши режется примерно до 16 ms и дополнительно suppress'ится по одинаковым координатам.

Это неплохо, но логика фиксированная и не зависит от состояния data channel / latency / congestion. На плохих сетях input path может всё равно быть шумным.

4. Host-side mouse injection очень прямолинейная

Файл: WindowsInputInjectionService.cs

Для move/down/up/click/wheel используется просто:

  • SetCursorPos(x, y)
  • далее mouse event.

Для desktop remote control это норм. Но если потом захотеть более тонкий relative/raw mode, текущая модель будет ограничением. Сейчас это не баг, а просто граница подхода.

5. Clipboard sync построен на polling и может быть шумным/хрупким

Файл: MainViewModel.Clipboard.cs

Сейчас буфер обмена проверяется циклом:

  • читать Clipboard
  • сравнивать с последним наблюдённым
  • при изменении — отправлять

Минусы:

  • polling по своей природе шумнее event-driven подхода;
  • Clipboard API в Windows капризный, и код местами просто глотает ошибки;
  • возможны race/состояния “не успел увидеть” при частых изменениях.

6. Clipboard echo suppression есть, но она довольно эвристическая

Файл: MainViewModel.Clipboard.cs

Сейчас защита от циклической пересылки держится на:

  • _lastAppliedRemoteClipboardText
  • временном окне 1500 ms
  • _lastSentClipboardText

Это practical workaround, но не строгая модель синхронизации. В edge-cases возможны ложные suppress / ложные resend.

Лучше: добавить явный clipboard message ID / version stamp, а не полагаться только на текст + таймер.

7. Получение clipboard полностью доверяет входящему тексту до лимита размера

Файл: MainViewModel.Clipboard.cs

Есть ограничение ClipboardMaxBytes — это хорошо. Но логика всё равно довольно простая: если текст не слишком большой, он просто ставится в локальный буфер обмена.

Риск: remote peer может шуметь clipboard updates и вмешиваться в локальную среду пользователя сильнее, чем ожидается.

Это не security-catastrophe, но для polished UX стоит подумать о более явной политике sync-mode.

8. Нет явного transport-level ordering/sequence для input событий

Файлы: payload model + datachannel usage

Судя по коду, input-события отправляются как обычные сообщения без отдельной sequence-модели на уровне приложения.

Если underlying channel гарантированно ordered/reliable — ок. Но приложение само этого явно не документирует и не контролирует.

Для критичных input-path сценариев это стоит хотя бы задокументировать.

9. Ctrl+Alt+Del сделан отдельным командным путём — это правильно

Файл: WindowsInputInjectionService.cs

Хорошо, что это не имитируется обычными keyboard payload'ами, а вынесено отдельно через SendSAS. Это более честный и понятный путь для secure attention sequence.

10. Много мест просто глотают ошибки

Файлы: input + clipboard loops

Во многих местах:

  • catch { }
  • или только тихий debug-log

Для MVP это удобно, чтобы не падать. Но когда начнутся реальные user-баги типа:

  • «иногда не отправляется Shift»
  • «иногда клипборд не доезжает»
  • «после reconnect залипают клавиши»

— отлаживать будет трудно.

Итог

Подсистема мыши/клавиатуры/clipboard у тебя уже неплохая и вполне живая. Основные проблемы тут — не в полном отсутствии логики, а в том, что часть решений пока эвристические и слишком tolerant к ошибкам. Самое важное место для улучшения — модель модификаторов клавиатуры и более строгая диагностика input/clipboard path.
