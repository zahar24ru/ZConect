Host Architecture Review — romantic-noyce / ZConect

Отдельный отчёт по host-сценарию: создание сессии, ожидание viewer, reconnect/reset, server API и host-side transport lifecycle.

Короткий вывод

Host-сторона у тебя уже продумана лучше, чем у типичного MVP: есть session create/refresh, повторное принятие viewer без полного закрытия сессии, WS reconnect, re-announce host state, lazy start локального видео только при offer с m=video.

Но именно host-режим сейчас содержит несколько наиболее хрупких архитектурных мест: доверие к server API, сложный reset/reconnect lifecycle и не до конца формализованная модель состояний.

Что анализировалось

  • client/UiApp/ViewModels/MainViewModel.Connection.cs
  • client/SessionClient/SessionApiClient.cs
  • server/internal/session/service.go
  • server/internal/api/handler.go
  • связанные host-side куски transport/datachannel lifecycle

Что в host-архитектуре уже хорошо

  • Host не стартует локальное видео раньше времени. Видео поднимается только если во входящем offer есть m=video.
  • После disconnect viewer host не закрывает сессию целиком, а пытается переинициализировать peer runtime.
  • Есть WS reconnect path для host'а отдельно от viewer'а.
  • Есть persisted session info для переиспользования после рестарта приложения.
  • Есть session refresh и обновление pass code без полной пересоздания сессии.

1. Самая опасная проблема: server API доверяет одному session_id

Файлы: SessionApiClient.cs, server/internal/api/handler.go, server/internal/session/service.go

Host вызывает:

  • CloseSessionAsync(baseUrl, sessionId)
  • RefreshSessionAsync(baseUrl, sessionId)

На сервере эти endpoints тоже работают только по session_id.

Проблема: если кто-то знает session ID, этого уже достаточно, чтобы:

  • закрыть host-сессию;
  • обновить пароль;
  • получить новый ws_token через refresh-path.

Вывод: с точки зрения host-режима это одна из главных архитектурных дыр.

Что нужно: owner token / host token / session secret, который не равен knowledge of session_id.

2. CreateSessionAsync сохраняет данные сессии даже если host connect/runtime поднялся неудачно

Файл: MainViewModel.Connection.cs

Сценарий сейчас такой:

  1. CreateSession API вернул response
  2. клиент делает ConnectWsAsync(...)
  3. после этого session info сохраняется в settings

Но в ConnectWsAsync при ошибке WS-подключения метод просто ставит статус ошибки и не кидает exception наверх.

Следствие: хост может сохранить в настройки session credentials, хотя runtime реально не поднялся корректно.

Лучше: возвращать из ConnectWsAsync явный результат успех/неуспех и сохранять persisted session только после успешного runtime bring-up.

3. Host reset path очень сложный и хрупкий

Файл: MainViewModel.Connection.cs — ResetForNewViewerAsync()

После disconnect viewer host делает не full teardown, а:

  • останавливает фоновые задачи;
  • disposes old WebRTC/runtime;
  • обнуляет много state flags вручную;
  • создаёт новый peer/data agent;
  • пересоздаёт signaling coordinator;
  • re-announces host state.

Это рабочая идея, но место очень хрупкое: здесь легко поймать двойные подписки, забытые state-флаги и несогласованность между old/new peer runtime.

4. Host и viewer используют разные reconnect semantics, но это не оформлено как state machine

Сейчас логика разумна:

  • viewer — full reconnect;
  • host — WS-only reconnect;
  • viewer disconnect — host reset for new viewer.

Но всё это живёт как набор методов и флагов, а не как явная state machine.

Риск: сложные edge-case баги вида:

  • peer disconnected пришёл во время reconnect;
  • refresh session прошёл, а ws reconnect не успел;
  • host reset и ws reconnect пересеклись по времени.

5. WS reconnect у host'а завязан на refresh endpoint, а refresh сам по себе недостаточно защищён

Файлы: WsReconnectLoopAsync(), handler.go

При host reconnect клиент получает fresh WS token через refresh. Это удобно, но усиливает проблему доверия к refresh API: если refresh слабо защищён, то он становится ключевым security gateway для host runtime.

6. В host path есть сильная зависимость от peer_state-сообщений как surrogate state model

Host при получении peer_state:

  • обновляет UI как «viewer connected»;
  • ре-анонсит host_ready.

Это работает, но peer_state сейчас слишком много значит:

  • presence signal,
  • readiness signal,
  • косвенный trigger orchestration.

Лучше: более явная signaling state model: joined, ready, paired, runtime_reset и т.п.

7. Host-side file transfer/runtime и remote-control subscriptions пересоздаются вместе с transport runtime

Это логично, но место очень чувствительное. При каждом reset создаются:

  • новый DataChannelCoordinator;
  • новый FileTransferService;
  • новые event subscriptions;
  • новые pending request ids.

Риск: если где-то UI-слой или окно FT держит старую ссылку на сервис/runtime, возможны висячие состояния и несогласованность после viewer reconnect.

8. Session service на сервере для host'а выглядит достаточно чисто

Плюсы:

  • reuse active session по machine_id — полезная идея;
  • refresh регенерирует только pass_code, login_code остаётся стабильным;
  • TTL хранится и переиспользуется;
  • есть lockout по join attempts.

Для MVP это нормальная session model.

9. Но при expire/close cleanup индексов местами недостаточно немедленный

Это не host-only баг, но хост-сценарий его чувствует сильнее. Например expired session может быть помечена как closed, но не всегда сразу убрана из индексов до отдельных cleanup-путей.

10. Host runtime сейчас слишком сильно завязан на MainViewModel

В host-сценарии ViewModel уже выступает как:

  • session controller;
  • signaling runtime manager;
  • WebRTC orchestrator;
  • file transfer bootstrapper;
  • UI state holder.

Это не просто MVVM anymore. Это означает, что дальнейшее усложнение host path почти гарантированно будет увеличивать хрупкость.

Что бы я исправлял первым именно для host-стороны

ПриоритетЧто менятьПочему
1Защитить refresh/close/create-owner flow отдельным host tokenЭто главный security риск host-архитектуры
2Сделать ConnectWsAsync с явным success/failure resultЧтобы не сохранять живую сессию, если runtime не поднялся
3Формализовать host runtime как state machineСнизит хаос вокруг reconnect/reset
4Разделить peer_state presence и readiness semanticsСделает signaling lifecycle честнее
5Выделить host runtime coordinator из MainViewModelУпростит сопровождение и снизит количество тонких багов

Итог

Host-архитектура у тебя уже неплохая и живая, но это один из самых сложных контуров проекта. Основные проблемы здесь — не в том, что «не работает», а в том, что слишком много критичного поведения держится на хрупкой orchestration-логике и слабой trust-модели server API. Именно host path я бы считал одной из главных зон инженерного долга на ближайшее время.
