Transport Architecture Review — romantic-noyce / ZConect

Специализированный отчёт по signaling, ICE, WebRTC transport и потоку удалённого рабочего стола.

Короткий вердикт

Транспортная архитектура проекта уже достаточно зрелая для MVP. В ней есть правильные инженерные решения: data channel как реальный connectivity proof, fallback DXGI → GDI, peer reset после disconnect, adaptive capture, relay как last resort.

Но самые опасные техдолги сейчас лежат не в захвате экрана, а в signaling lifecycle и в том, как клиент делает выводы о качестве ICE-маршрута.

Что именно анализировалось

  • client/WebRtcTransport/SignalingCoordinator.cs
  • client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs
  • client/UiApp/ViewModels/MainViewModel.Connection.cs
  • client/UiApp/ViewModels/MainViewModel.Video.cs
  • server/internal/signaling/handler.go
  • server/internal/signaling/hub.go

Что в архитектуре уже хорошо

  • Signaling relay отделён от session API. Это правильно и упрощает reasoning.
  • Data channel open используется как реальное доказательство connectivity. Это сильное решение.
  • Host и viewer имеют разный reconnect path. Это сложнее, но по смыслу верно.
  • Видео-пайплайн уже не наивный: DXGI, GDI fallback, scaling, buffer reuse, adaptive capture.
  • Есть идея ICE upgrade monitor. То есть проект уже пытается быть не просто «соединились как получится», а оптимизировать путь.

1. Signaling lifecycle: основная слабая точка

Серверный WebSocket слой работает как тупой relay: он не понимает offer/answer/ice как сущности и не буферизует критичные сообщения. Это допустимо для MVP, но приводит к тому, что клиенту приходится компенсировать потерю timing-семантики.

Симптомы уже видны в коде клиента:

  • deferred caller start;
  • ожидание peer_state;
  • таймерный fallback старта offer.

Проблема: signaling-состояние по сути размазано между сервером и клиентом, но сервер почти ничего не знает, поэтому вся сложность оседает в клиенте.

2. Route inference по observed ICE candidates — ненадёжная телеметрия

Сейчас тип маршрута фактически выводится по строкам вида typ host, typ srflx, typ relay, которые были замечены в signaling-потоке.

Но это не эквивалентно selected candidate pair.

Из этого следуют реальные риски:

  • UI может показывать не тот route, который реально используется;
  • ICE upgrade monitor может принимать неверные решения;
  • можно получить лишние ICE restart на уже хорошем канале.

Правильнее: вытаскивать selected/active candidate pair из реальных WebRTC stats, если библиотека даёт такую информацию.

3. ICE-стратегия по идее сильная, но логика принятия решений местами грубая

Подход All ICE methods first, upgrade later сам по себе хороший. Он лучше, чем вручную делать строгую последовательность LAN → STUN → TURN.

Однако monitor сейчас зависит от:

  • network change events;
  • условного route type;
  • RTT;
  • серии retry/restart.

Что тут не идеально:

  • network change events бывают шумными;
  • RTT сам по себе не всегда означает лучший путь;
  • route type сейчас inferred, а не selected;
  • restart policy стоит сильнее ограничить budget/cooldown-логикой.

4. ICE restart через ручную правку SDP — рабочий, но хрупкий hack

ForceIceRestart() заменяет ice-ufrag и ice-pwd через regex. Это часто срабатывает, но остаётся workaround-ом.

Риск: поведение зависит от того, насколько библиотека MixedReality WebRTC терпимо относится к таким restart'ам без более высокого уровня API.

Рекомендация: если в библиотеке есть штатный механизм ICE restart, переходить на него. Если нет — хотя бы явно документировать это место как controlled workaround.

5. Reconnect/reset lifecycle уже очень сложный

Сейчас в клиенте есть несколько пересекающихся веток runtime-логики:

  • ConnectWsAsync
  • ConnectWsWithAutoIcePriorityAsync
  • CleanupConnectionAsync
  • ResetForNewViewerAsync
  • WsReconnectLoopAsync
  • IceUpgradeMonitorLoopAsync

Это не ошибка прямо сейчас, но это уже зона высокой хрупкости. В будущем именно тут будут жить самые неприятные race/regression-баги.

6. Поток удалённого рабочего стола спроектирован лучше, чем можно ожидать от MVP

Пайплайн на host:

  • выбор display / virtual desktop;
  • quality profile → target resolution/fps;
  • DXGI single output или DXGI multi / GDI fallback;
  • double-buffered pinned frame storage;
  • ExternalVideoTrackSource → local video track → transceiver.

На viewer:

  • remote argb frame;
  • копия в pooled managed buffer;
  • рендер в WriteableBitmap.

Для MVP это уже очень неплохо.

7. Но MixedRealityPeerConnectionAgent уже совмещает слишком много уровней ответственности

Сейчас один класс управляет одновременно:

  • PeerConnection;
  • ICE candidate callbacks;
  • SDP lifecycle;
  • local track attach;
  • capture thread;
  • DXGI path;
  • GDI path;
  • scaling;
  • viewer buffer pool;
  • remote frame delivery.

Вывод: это уже не просто peer wrapper. Его стоит дробить хотя бы на:

  • peer connection wrapper;
  • capture pipeline;
  • remote frame adapter.

8. Viewer-side video path делает лишние копии, и это может стать bottleneck

Сначала кадр копируется из native frame в managed buffer, потом ещё в backbuffer WriteableBitmap.

Для текущего этапа ок. Но если потом захочется:

  • более высокие FPS;
  • большие разрешения;
  • слабые клиентские машины;

— viewer rendering path станет одним из первых кандидатов на оптимизацию.

9. Multi-monitor / All displays — честно рабочий, но потенциально дорогой путь

Для режима All архитектура ожидаемо тяжелее. Это не баг, а инженерное ограничение:

  • большая область захвата;
  • возможный GDI fallback;
  • много пикселей на кадр;
  • дополнительное масштабирование.

Важно лишь не обещать, что multi-monitor режим будет таким же лёгким, как single display.

Отдельно: file transfer поверх data channel

Файловый обмен использует ту же transport-базу и тоже относится к transport/runtime уровню, поэтому его стоит оценивать здесь же.

10. Протокол file transfer в целом удачный

  • binary chunks вместо Base64 — правильно;
  • есть отдельные meta / chunk / end / ack / error события;
  • есть relative path для папок;
  • есть hash-check и temp file на приёмнике.

11. ACK-модель сейчас логически смазана

Отправитель считает передачу завершённой сразу после file_end, хотя приёмник ещё только начинает финальную проверку hash и перемещение файла. Это создаёт race между UI success-state и реальным подтверждением успешного приёма.

12. Binary chunks требуют жёсткого лимита размера

Сейчас large chunk может привести к лишнему расходу памяти и дорогой распаковке. Для transport-уровня это важный hardening-пункт.

13. Control-channel файловой панели может стать тяжёлым из-за recursive dir size

Подсчёт полного размера директорий прямо в listing-ответе — дорогая операция и не очень подходит для интерактивного транспортного протокола.

14. Remote delete/create/file request требуют более чёткой trust-модели

Сейчас это очень широкие операции над файловой системой. Для режима доверенной удалённой помощи это может быть приемлемо, но transport/security слой должен это явно осознавать и ограничивать при необходимости.

Итог

Если честно: транспортная часть проекта уже сильнее, чем у многих MVP. Самые важные слабые места сейчас — это не “не умеет работать”, а сложность runtime-поведения, недостаточно точная телеметрия ICE и несколько важных краевых сценариев в file transfer. Это хорошие проблемы: значит, база уже есть, и дальше речь идёт о доводке инженерного качества, а не о спасении архитектуры с нуля.
