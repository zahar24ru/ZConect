Viewer Architecture Review — romantic-noyce / ZConect

Отдельный отчёт по viewer-сценарию: join, caller start, reconnect, ICE upgrade, input/video/file flows со стороны зрителя.

Короткий вывод

Viewer-сторона у тебя уже сделана довольно умно: есть единая точка входа в подключение, fast-connect подход для ICE, health-check по ping/pong, full reconnect path, синхронизация дисплеев/настроек видео, нормальная обработка input surface.

Но viewer-режим остаётся самым сложным transport-runtime сценарием во всём приложении. Именно здесь живут основные риски гонок, ложных состояний и не до конца надёжной reconnect-логики.

Что анализировалось

  • client/UiApp/ViewModels/MainViewModel.Connection.cs
  • client/UiApp/ViewModels/MainViewModel.Input.cs
  • client/UiApp/ViewModels/MainViewModel.Video.cs
  • client/SessionClient/SessionApiClient.cs
  • server/internal/api/handler.go

Что уже хорошо

  • Есть единая точка входа ConnectAsViewerAsync() — это хорошая основа.
  • Fast connect + upgrade later — правильное направление для ICE.
  • WaitForDataChannelOpenAsync() ждёт реальное connectivity proof, а не просто факт обмена candidate'ами.
  • Viewer reconnect делает full runtime rebuild, что безопаснее, чем пытаться латать всё in-place.
  • Есть ping/pong health check и попытка восстановления при silence.
  • Input mapping по remote surface выглядит аккуратно и с учётом letterbox/scale.

1. Join API + viewer trust model слишком опираются на одноразовые коды и session_id

Файлы: SessionApiClient.cs, handler.go

С точки зрения viewer сценарий начинается нормально: join идёт по login/pass. Но дальше viewer получает:

  • session_id
  • ws_token

А затем reconnect-path viewer'а фактически опирается на refresh(session_id), который на сервере недостаточно защищён.

Вывод: viewer reconnect security сейчас наследует ту же проблему, что и host-side refresh API.

2. Viewer считает подключение успешным чуть раньше, чем это хотелось бы

Файл: ConnectAsViewerAsync()

После ConnectWsWithAutoIcePriorityAsync(...) код продолжает:

  • открывать окно remote screen;
  • ставить SetStatus($"Подключено: ...").

Но внутри fast-connect path возможен сценарий, где data channel так и не открылся вовремя, и код только запускает retry loop со статусом ICE: ожидание соединения....

Риск: UI верхнего уровня может показать слишком оптимистичное состояние подключения.

Лучше: возвращать из connect path более точный результат:

  • Connected
  • ConnectingButNotConfirmed
  • Failed

3. Caller start всё ещё опирается на хрупкую signaling workaround-логику

Файл: ConnectWsAsync()

Viewer — это caller. Но because server is a dumb relay, viewer не может просто сразу послать offer. Поэтому у тебя есть:

  • _callerStartDeferred
  • ожидание peer_state
  • таймерный fallback через 1500 ms

Это рабочий workaround, но архитектурно слабое место. Именно viewer path сильнее всего зависит от того, успеет ли signaling timing совпасть правильно.

4. Viewer reconnect path очень сложный и может легко создавать ложные success-состояния

Файл: WsReconnectLoopAsync()

Viewer reconnect делает full reconnect — это правильно. Но после него код:

  • повторно поднимает WS
  • повторно создаёт WebRTC/runtime/data channels
  • открывает remote screen window
  • ставит статус Переподключено

Проблема: reconnect success сейчас завязан скорее на успешный runtime restart, чем на подтверждённый рабочий media/data path.

То есть viewer reconnect может считаться успешным до того, как реально восстановился usable transport.

5. Health-check по ping/pong правильный, но reconnect trigger довольно грубый

Файл: MainViewModel.Video.cs

Если нет pong 30 секунд — viewer запускает reconnect.

Плюс: это practical safety net.

Минус: логика опирается только на pong silence и не различает:

  • мертвый datachannel
  • подвисший control path
  • живой media path при деградировавшем DC
  • временные лаги/заморозки UI

В целом это acceptable для MVP, но viewer reconnect политика пока довольно грубая.

6. Viewer-side ICE upgrade решения принимаются по неидеальной телеметрии

Файл: MainViewModel.Connection.cs

Viewer — единственная сторона, которая запускает ICE upgrade monitor и делает restart как caller. Значит, именно viewer больше всего зависит от качества route inference.

А route сейчас определяется по observed candidate types, а не по selected pair.

Следствие: именно viewer runtime может ошибаться с upgrade/degrade решениями чаще всего.

7. Viewer input path выглядит хорошо, но fire-and-forget sender'ы могут скрывать ошибки

Файл: MainViewModel.Input.cs

Mouse/keyboard отправляются через SafeSendMouseAsync / SafeSendKeyboardAsync как fire-and-forget задачи.

Это норм для responsiveness, но есть и минус: ошибки и задержки в datachannel path могут долго оставаться скрытыми, особенно если соединение уже частично развалилось.

8. Координатный mapping viewer → remote host сделан аккуратно

Файл: MainViewModel.Input.cs

Это сильное место. Учтены:

  • letterbox offsets;
  • Uniform scaling;
  • capture rect offsets;
  • clamp в допустимые координаты.

С точки зрения viewer UX это хороший фундамент.

9. Viewer path смешивает UI-успех, transport-успех и session-успех

Сейчас в нескольких местах статусы типа:

  • «Подключено»
  • «Переподключено»
  • «WS: peer_state»
  • «ICE: ожидание соединения...»

могут пересекаться и перетирать друг друга.

Вывод: viewer runtime просит разделения как минимум на 3 слоя состояний:

  • Session/WS status
  • Transport status
  • Media/UI status

10. Viewer-side file transfer bootstrap пересоздаётся на каждый reconnect

Это логично, но нужно внимательно следить, чтобы UI FT-окно не держало старую ссылку на сервис/runtime после reconnect. Иначе появятся «живые», но уже оторванные от transport слоя объекты.

11. MainViewModel уже слишком много знает о viewer runtime

Для viewer path ViewModel сейчас держит:

  • join/session orchestration;
  • WS lifecycle;
  • caller start logic;
  • ICE monitoring;
  • RTT/health checking;
  • remote video rendering hooks;
  • input sending;
  • file transfer bootstrap.

Это уже не просто VM, а viewer runtime coordinator. И это главный источник будущей сложности.

Что бы я чинил первым именно для viewer-стороны

ПриоритетЧто менятьПочему
1Разделить states: WS / transport / media / UIУбрать ложные success-состояния
2Возвращать из connect/reconnect path явный результат подтверждённого подключенияЧтобы viewer не считал success слишком рано
3Сделать signaling readiness честнее и убрать часть defer/timer логикиЭто главный хрупкий участок caller path
4Перевести ICE route detection на selected pair statsViewer сильнее всех зависит от корректности upgrade monitor
5Вынести viewer runtime coordinator из MainViewModelСнизить сложность и риски гонок

Итог

Viewer-сторона у тебя уже технически сильная, но она же и самая сложная. Основная проблема не в том, что логика неправильная, а в том, что слишком много разных типов состояний и переходов живут в одном месте и не до конца формализованы. Именно viewer path я бы считал главным кандидатом на будущую state-machine/coordination реорганизацию.
