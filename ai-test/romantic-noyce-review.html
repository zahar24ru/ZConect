Code Review — romantic-noyce / ZConect

Проект: /media/sf_DW/romantic-noyce

Краткий вывод

Проект уже выглядит как рабочий MVP с нормальной структурой: клиент разбит на модули, сервер вынесен отдельно, документации много. Это хороший фундамент. Основные проблемы не в том, что код «развален», а в трёх местах:

  • есть дыры в безопасности и доверии к запросам на сервере;
  • в клиенте встречаются опасные паттерны завершения/ошибкообработки;
  • есть несколько архитектурных мест, которые сейчас ещё терпимы для MVP, но потом начнут мешать.

Что удалось проверить

  • Структуру репозитория и ключевые файлы клиента/сервера.
  • Серверную часть Go — просмотр кода + сборка/тесты go build ./... и go test ./....
  • Клиентскую часть .NET/WPF удалось уже проверить лучше: .NET 8 SDK установлен, но сборка на Linux упирается в Windows-targeting.
error NETSDK1100: To build a project targeting Windows on this operating system, set the EnableWindowsTargeting property to true.

Найденные проблемы и улучшения

1. Серверные endpoints доверяют клиенту слишком сильно

Файлы: server/internal/api/handler.go

Проблема: /api/v1/session/close и /api/v1/session/refresh принимают только session_id. То есть любой, кто узнал ID сессии, потенциально может закрыть её или обновить пароль, если у него есть доступ к API.

Почему это плохо: для удалённого доступа это критичный контур доверия. session_id не должен быть единственным подтверждением владения сессией.

Что улучшить:

  • требовать отдельный host-token / owner-token для refresh/close;
  • разделить токены host/viewer;
  • не делать управление сессией только по knowledge-based идентификатору.

2. ws_token сейчас заглушка, а WebSocket — ключевая часть безопасности

Файлы: README.md, server/README.md, косвенно server/internal/auth/token.go / signaling handler

В документации прямо указано, что боевой ws_token ещё не доделан. Для MVP это ок, но для реального использования это одно из главных мест риска.

Что улучшить:

  • сделать короткоживущий подписанный токен с role/session binding;
  • валидировать token на upgrade в /ws;
  • добавить replay protection или хотя бы очень короткий TTL.

3. Нет ограничения тела JSON-запроса

Файл: server/internal/api/handler.go

Во всех HTTP handlers используется обычный json.NewDecoder(r.Body) без http.MaxBytesReader.

Риск: лишняя поверхность для DoS / memory pressure на мусорных больших запросах.

Что улучшить: перед decode ограничить размер тела, например 4–16 KB для этих endpoint'ов.

4. join валидирует длину кодов, но не проверяет, что это именно цифры

Файл: server/internal/api/handler.go

Сейчас проверяется только len(req.LoginCode) != 8 || len(req.PassCode) != 8.

Что улучшить: явно валидировать формат: только [0-9]{8}. Это мелочь, но интерфейс и API будут честнее согласованы.

5. Закрытые/протухшие сессии не всегда сразу удаляются из индексов

Файл: server/internal/session/service.go

В Join при expired-сессии состояние меняется на StateClosed, но запись продолжает жить в индексах до prune/cleanup. Это не баг-катастрофа, но добавляет путаницу и лишнее состояние.

Что улучшить: централизовать cleanup индексов для expired/closed session прямо в критических ветках.

6. Клиент завершает приложение через Environment.Exit(0)

Файл: client/UiApp/MainWindow.xaml.cs

В конце OnClosingAsync вызывается и Application.Current.Shutdown(), и затем Environment.Exit(0).

Почему это плохо:

  • жёсткий выход может оборвать flush/dispose/async cleanup;
  • усложняет корректное завершение WPF lifecycle;
  • маскирует реальные зависания shutdown вместо их исправления.

Что улучшить: оставить один контролируемый путь завершения, а не принудительный процесс-килл.

7. В клиенте много мест с catch { /* ignore */ }

Файлы: особенно MainWindow.xaml.cs, вероятно и другие UI-модули

Для MVP это помогает не падать, но в реальности такие блоки скрывают проблемы и ломают диагностику.

Что улучшить:

  • логировать хотя бы debug/warn;
  • использовать единый helper для safe-exec с логированием;
  • молча игнорировать только truly harmless сценарии.

8. MainViewModel очень большой и тянет на god-object

Файл: client/UiApp/ViewModels/MainViewModel.cs + partial pieces

Хорошо, что он уже разбит на partial-файлы, но объект всё равно держит слишком много ответственности: сеть, clipboard, input, session lifecycle, file transfer, UAC, contacts, UI state, timers, diagnostics.

Риск: любое изменение начинает цеплять всё сразу, растёт вероятность регрессий.

Что улучшить:

  • выделить отдельные coordinator/service-объекты: session lifecycle, remote desktop, clipboard sync, transfer orchestration;
  • оставить во ViewModel в основном binding-state и команды.

9. Жёсткая привязка UI к Win32/NotifyIcon прямо в code-behind

Файл: client/UiApp/MainWindow.xaml.cs

Это допустимо для MVP, но дальше будет мешать тестируемости и сопровождению.

Что улучшить: вынести tray/notification/window flashing в отдельный UI service.

10. В API логируется client IP, но нет нормальной reverse-proxy стратегии

Файл: server/internal/api/handler.go

clientIP() берёт только r.RemoteAddr. Если сервер будет стоять за reverse proxy, логи и rate limit могут стать неинформативными.

Что улучшить: либо явно документировать direct mode only, либо аккуратно поддержать доверенный proxy режим.

11. Несогласованность naming/branding

Файлы: по всему проекту — ZConect, ZConnect, Zconnect

Это не bug, но влияет на доверие и аккуратность продукта.

Что улучшить: выбрать единый canonical brand name и оставить старое имя только там, где ломается совместимость (repo/package IDs).

12. Нет автоматической технической проверки в CI, по крайней мере в корне проекта она не видна

Не обнаружены явные workflow/CI-конфиги в просмотренной структуре.

Факт проверки: серверные тесты go test ./... проходят, клиентскую Windows-сборку нужно гонять либо на Windows runner, либо на Linux с корректно включённым Windows-targeting.

Что улучшить:

  • Go: go test ./..., go vet
  • .NET: build + tests на .NET 8 runner
  • отчёт по артефактам релиза

Подтверждённые сильные стороны

  • Хорошая модульность по папкам: ScreenCapture, SessionClient, WebRtcTransport, FileTransfer.
  • Есть документация по архитектуре, API, деплою, релизу.
  • Для UI уже есть попытка держать MVVM и выносить логику в partial viewmodel.
  • Сервер маленький и читаемый — это плюс для MVP.
  • Есть тестовый проект client/ZConect.Tests, это хороший знак.

Ниже — отдельный технический разбор не только по коду, но и по runtime-архитектуре: как живут клиент и сервер, как устроена ICE-логика, и как формируется/едет поток удалённого рабочего стола.

13. Клиентская orchestration-логика уже перегружена

Файлы: client/UiApp/ViewModels/MainViewModel.Connection.cs, MainViewModel.Video.cs, MainViewModel.cs

MainViewModel сейчас управляет почти всем runtime:

  • создание/подключение сессии;
  • WS lifecycle;
  • reconnect / reset;
  • ICE upgrade monitor;
  • data channel init;
  • clipboard / cursor loops;
  • video stats / RTT / health checks.

Вывод: для MVP ещё допустимо, но это уже не просто ViewModel, а фактически runtime orchestrator. Дальше лучше выносить это в отдельные coordinator/service-слои.

14. Signaling-сервер слишком «тупой», поэтому клиенту приходится компенсировать это костылями

Файлы: server/internal/signaling/handler.go, client/UiApp/ViewModels/MainViewModel.Connection.cs

Сервер просто relay'ит сообщения между двумя peer'ами. Это хорошее MVP-решение, но из-за отсутствия очереди/буферизации клиент вынужден сам обходить lost-offer сценарий:

  • deferred caller start;
  • ожидание peer_state;
  • таймерный fallback на старт offer через 1500 ms.

Вывод: signaling архитектура рабочая, но хрупкая. Лучше либо добавить server-side readiness handshake, либо буферизацию критичных signaling-сообщений.

15. Возможна race-condition при подключении двух peer'ов в одну сессию

Файл: server/internal/signaling/handler.go

Проверка len(peers) >= 2 и последующий hub.Add(peer) не атомарны. При почти одновременном подключении двух клиентов это теоретически может позволить проскочить лишнему peer'у.

Что улучшить: резервировать слот атомарно внутри hub/session manager.

16. Определение ICE route сделано по observed candidates, а не по selected pair

Файлы: client/WebRtcTransport/SignalingCoordinator.cs, MainViewModel.Connection.cs

Сейчас тип маршрута выводится по последним замеченным ICE candidate types (host / srflx / relay). Но кандидат, который был замечен, не обязательно является тем, который реально стал selected/nominated pair.

Риск:

  • ложные выводы о текущем route;
  • неправильные решения в ICE upgrade monitor;
  • лишние ICE restart.

Что улучшить: брать active/selected candidate pair из реальных WebRTC stats, если библиотека это позволяет.

17. ICE upgrade стратегия хорошая по идее, но местами слишком шумная

Файл: MainViewModel.Connection.cs

Текущий подход all candidates first, upgrade later сам по себе разумный и лучше многих sequential fallback-схем. Но monitor опирается на:

  • network change events;
  • грубый route inference;
  • серии restart'ов при подозрении на degradation.

Риск: шумные рестарты при VPN / virtual adapters / сетевых дребезгах.

Что улучшить: ввести cooldown, restart budget, и опираться ещё и на packet loss / bitrate / selected pair stats.

18. ICE restart сделан через ручную правку SDP

Файл: client/WebRtcTransport/SignalingCoordinator.cs

ForceIceRestart() меняет a=ice-ufrag и a=ice-pwd через regex. Это рабочий workaround, но хрупкий.

Риск: если библиотека ожидает штатный restart API или internal state machine более сложная, ручная замена SDP может вести себя нестабильно на части сценариев.

19. Видео-конвейер на host сделан уже неплохо

Файлы: client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs, MainViewModel.Video.cs

Плюсы текущей реализации:

  • DXGI как основной путь + GDI fallback;
  • поддержка single display и all displays;
  • double buffering для захвата и кодировщика;
  • adaptive capture speed / frame skip;
  • viewer-side buffer pool.

Для MVP это уже сильная часть проекта.

20. Но MixedRealityPeerConnectionAgent уже стал слишком большим runtime-компонентом

Файл: client/WebRtcTransport/MixedRealityPeerConnectionAgent.cs

Внутри одного класса сейчас живут:

  • PeerConnection lifecycle;
  • transceiver management;
  • local track attach;
  • DXGI capture;
  • GDI capture;
  • scaling;
  • adaptive FPS;
  • remote frame delivery;
  • viewer buffer pooling.

Вывод: это не баг само по себе, но дальше сопровождать такой класс будет тяжело. Стоит дробить на capture pipeline / peer wrapper / viewer frame adapter.

21. Viewer-side video path делает минимум одну лишнюю полную копию кадра

Файлы: MixedRealityPeerConnectionAgent.cs, MainViewModel.Video.cs

Сначала кадр копируется из native frame в managed buffer, потом ещё переписывается в WriteableBitmap. Для MVP это нормально, но на высоких разрешениях и слабых ПК может стать bottleneck.

22. Подход с ожиданием data channel как доказательства connectivity — правильный

Файл: MainViewModel.Connection.cs

Это сильное место архитектуры. Ты ждёшь не просто обмен ICE/SDP, а реальное открытие data channel (и вторично first remote frame). Это гораздо честнее, чем считать успешным сам факт обмена кандидатами.

Отдельный аудит: передача файлов

Файловый обмен в проекте уже выглядит как рабочий модуль, а не просто набросок: есть queue, chunking, hash-проверка, binary path без Base64, относительные пути для папок, запросы на dir list / create folder / delete. Но есть несколько важных багов и рисков.

23. Отправитель помечает transfer как Completed до получения ACK от получателя

Файл: client/FileTransfer/FileTransferService.cs

После SendFileEndAsync() отправитель сразу вызывает RaiseProgress(... Completed) и RaiseCompleted(...). Но реальный успех ещё не подтверждён: получатель только потом проверяет hash, двигает файл и отправляет ACK.

Риск: UI может показать «файл отправлен», а потом прилетит file_ack success=false или ошибка на стороне приёма.

Что улучшить: считать outgoing transfer завершённым только после положительного ACK.

24. Нет ограничения на размер входящего binary chunk / payload

Файлы: client/WebRtcTransport/DataChannelCoordinator.cs, client/FileTransfer/FileTransferService.cs

Получатель принимает binary chunk целиком в память, а затем при необходимости ещё и распаковывает его целиком через GZip. Явного предела на размер chunk'а на принимающей стороне не видно.

Риск: peer может отправить oversized chunk и устроить memory pressure / OOM / CPU spike на распаковке.

Что улучшить: ввести жёсткий max chunk size на wire-уровне и отклонять всё, что выше лимита.

25. Сжатие GZip делается покусково, что даёт лишнюю CPU-нагрузку и нестабильный выигрыш

Файл: client/FileTransfer/FileTransferService.cs

Каждый chunk независимо gzip-сжимается и независимо распаковывается. Это рабоче, но не оптимально:

  • теряется выгода межчанкового контекста;
  • растёт CPU overhead;
  • на части файлов выгода будет спорной.

Это не критический баг, но архитектурно лучше либо не сжимать вовсе на datachannel-уровне, либо делать это более осмысленно.

26. Рекурсивный расчёт размера папки при dir list может быть очень дорогим

Файл: client/UiApp/ViewModels/MainViewModel.FileTransfer.cs

GetDirectorySizeSafe() делает EnumerateFiles(..., AllDirectories).Sum(...) для каждой директории. На больших дисках и глубоких деревьях это может тормозить ответ dir list очень сильно.

Риск: зависания/долгие паузы файловой панели и тяжёлые запросы по control channel.

Что улучшить: не считать полный recursive size при обычном listing или делать это лениво/по требованию.

27. Directory.Delete(..., recursive: true) без песочницы — очень опасный remote operation

Файл: client/UiApp/ViewModels/MainViewModel.FileTransfer.cs

Удалённая сторона может запросить delete любого пути, и host попытается удалить файл/директорию по абсолютному пути.

Риск: слишком широкие полномочия для remote file operations. Для trusted-support сценария это может быть допустимо, но для безопасности это очень сильный рычаг.

Что улучшить: хотя бы ограничить операции выбранным root / рабочей областью или ввести режим подтверждения опасных операций.

28. Сервис уже использует правильные инженерные идеи

Файл: client/FileTransfer/FileTransferService.cs

  • переход на binary chunks вместо Base64 — хороший шаг;
  • есть hash verification;
  • есть temp file + move в final path;
  • есть queue для последовательной отправки;
  • есть поддержка передачи папок через relative path.

То есть модуль уже неплохой — его надо не переписывать, а дожимать по корректности и безопасности.

Итог

У проекта хороший MVP-фундамент. Главная работа сейчас — не переписывать всё, а докрутить безопасность, диагностику, signaling lifecycle, честную телеметрию ICE и корректность file transfer ACK/validation. Видео-пайплайн уже неплохой, а вот reconnect/upgrade/runtime orchestration и file-transfer safety — это места, куда стоит смотреть в первую очередь.
